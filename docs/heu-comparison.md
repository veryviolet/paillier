# Чем `heu` быстрее и что из этого перенимаем

Разбор по коду: `heu/library/algorithms/paillier_zahlen` (Apache 2.0,
это и есть `SchemaType.ZPaillier`) против `fast-paillier 0.3.2`
(MIT OR Apache-2.0), на котором стоит наш пакет.

Замерено на одном наборе, ключ 2048 бит, Python 3.10, один поток:
шифрование **0.69 мс** у `heu` против **9.36 мс** у нас. Разница
тринадцатикратная при том, что обе считают длинной арифметикой на C.
Значит дело не в языке — ниже разобрано, в чём.

## Шифрование

Обе стороны считают `c = g^m · r^n mod n²`, но по-разному.

### `g^m` — паритет

При `g = n+1` бином даёт `g^m ≡ 1 + m·n (mod n²)`: одно умножение
вместо возведения в степень. Делают обе.

`heu` (`encryptor.cc:44`):

```cpp
BigInt gm = pk_.n_ * m + 1;  // no need mod
```

`fast-paillier` (`encryption_key.rs:75`):

```rust
let a = (Integer::one() + &x * self.n()) % self.nn();
```

### `r^n` — здесь и лежит разрыв

`fast-paillier` (`encryption_key.rs:78`) считает буквально:

```rust
let b = nonce.pow_mod_ref(self.n(), self.nn())
```

Основание `nonce` **случайное**, показатель `n` — 2048 бит, модуль `n²`
— 4096 бит. Полное возведение в степень, и ничего предвычислить нельзя:
основание каждый раз новое.

`heu` (`encryptor.cc:26-31`) считает иначе:

```cpp
BigInt Encryptor::GetRn() const {
  BigInt r = BigInt::RandomExactBits(pk_.key_size_ / 2);
  return pk_.m_space_->PowMod(*pk_.hs_table_, r);
}
```

Три отличия сразу, и каждое режет цену:

1. **Основание фиксированное.** Вместо `r^n` берётся `h^r`, где `h`
   заготовлено при генерации ключа. Это вариант Дамгорда–Жюрика, а не
   самодеятельность: неразличимость сохраняется.
2. **Таблица окон.** `hs_table_` — предвычисленные степени фиксированного
   основания. Возможна ровно потому, что основание не меняется.
3. **Показатель вдвое короче.** `key_size_ / 2` — 1024 бита вместо 2048.

Итого вместо возведения случайного основания в 2048-битную степень —
табличное возведение фиксированного основания в 1024-битную. Отсюда и
берётся тринадцатикратная разница.

### Пространство Монтгомери

`heu` держит модуль в `m_space_` и считает `MulMod`/`PowMod` в нём
(`encryptor.cc:46,49`), с явными переходами `MapIntoMSpace` /
`MapBackToZSpace`. `fast-paillier` пользуется обычными `%` и `.modulo()`
поверх GMP. Для многократных операций по одному модулю Монтгомери
дешевле, но это уже не порядок величины.

## Расшифровка

Здесь **обе** делают китайскую теорему об остатках, и замер это
подтверждает: 2.79 мс у `heu` против 5.32 мс у нас — разница вдвое, а
не втрое-впятеро.

`heu` (`decryptor.cc:38-47`) — явно, порознь по `p²` и `q²`, со сборкой
через `p_inv_mod_q_`. `fast-paillier` (`decryption_key.rs:80`) — тем же
приёмом, но спрятанным в `crt_mod_nn.exp`.

## Что переносим

| приём | у нас | у `heu` | безопасно |
|---|---|---|---|
| `g^m = 1 + m·n` | есть | есть | — |
| КТО при расшифровке | есть | есть | — |
| фиксированное основание `h` вместо `r^n` | нет | есть | требует правки генерации ключа |
| таблица окон для `h` | нет | есть | да, чистая арифметика |
| короткий показатель `n/2` бит | нет | есть | следствие перехода на `h` |
| пространство Монтгомери | нет | есть | да, чистая арифметика |

Первые два уже есть — их и переносить незачем.

Главный перенос — переход с `r^n` на `h^r` с таблицей и коротким
показателем. Он трогает **схему**, а не только арифметику: `h`
порождается при генерации ключа, и его корректность — условие
стойкости. Приём стандартный и опубликованный, но вводить его надо с
проверкой, а не «по аналогии».

Пространство Монтгомери и таблица окон безопасны: они не меняют
результат, только скорость.

Чего в этом списке **нет** намеренно: заготовленного запаса готовых
`r^n`. Он дал бы ещё, но повторное использование `r` ломает
семантическую безопасность, и вводить его можно только с явной
гарантией однократного расхода каждого значения.
