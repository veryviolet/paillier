# Чем `heu` быстрее и что из этого перенимаем

## Сводка

Ключ 2048 бит, один набор, одна машина, `N = 200`. `paillier` — этот
пакет.

| метрика | `paillier` | `heu` | кто лучше |
|---|---|---|---|
| шифрование, все ядра (эл/с) | **4403** | 1378 | `paillier` ×3.2 |
| шифрование, одно ядро (эл/с) | 686 | **1378** | `heu` ×2.0 |
| сложение (мкс на слагаемое) | **6.7** | 9.8 | `paillier` ×1.5 |
| расшифровка (мс) | 3.65 | **2.79** | `heu` ×1.3 |
| шифротекст (байт) | **511–512** | 524 | `paillier` |
| ключ 2048 (с, медиана из 5) | 2.92 | **1.18** | `heu` ×2.5 |
| ключ 3072 (с, медиана из 5) | 16.15 | **2.94** | `heu` ×5.5 |
| ошибка суммы, 10⁵ неотрицательных | **1.17e-06** | 5.00e-04 | `paillier` ×430 |

Параллелизм есть только у нас: у `heu` `encrypt_many` нет вовсе, там
питоновский цикл. Поэтому первые две строки — это одно и то же
измерение, поданное двумя способами, и обе надо читать вместе.

Разброс у генерации ключа огромный — при 3072 битах от 9.1 до 32.3
секунды, — поэтому там медиана, и одиночный замер там не значит ничего.

### Откуда берётся каждая разница

**Шифрование в одном ядре, ×2 в пользу `heu`** — это АРИФМЕТИКА, а не
плата за стойкость. Разрыв 731 мкс на элемент; меры стойкости в нём
занимают около 44 мкс (постоянное чтение таблицы ~14, полноразмерный
вычет в нулевой записи ~30), то есть **6 %**. Остальные 94 % — умножение
по модулю в пространстве Монтгомери НА ЛИМБАХ, которого у нас нет: тот
же приём поверх `rug::Integer` замерен и замедляет на 15 %.

**Расшифровка, ×1.3 в пользу `heu`** — наоборот, плата за стойкость
целиком: `mpz_powm_sec` вместо `mpz_powm`, замерено 1.54–1.55×. С
обычным возведением вышло бы около 2.4 мс, то есть быстрее `heu`.

**Ключ, ×2.5 и ×5.5 в пользу `heu`** — прямое следствие требования к
ключу. Мы ищем БЕЗОПАСНЫЕ простые (`p = 2p′+1`, `p′` тоже просто), `heu`
— блюмовы (`key_generator.cc:34`). Второе условие режет плотность
кандидатов примерно как `1/ln N`, отсюда и разница. Здесь я прежде
утверждал обратное («4.87 с против ~25»); замер это опровергает.

**Ошибка суммы, ×430 в пользу нас** — правило округления: мы к
ближайшему, `heu` усекает к нулю. На знакопостоянных данных усечение
даёт линейный снос. На симметричных данных разницы нет.

## Различия в безопасности

Проверено по исходникам `heu` (`paillier_zahlen`), не по памяти.

| | `paillier` | `heu` |
|---|---|---|
| простые | безопасные, `p = 2p′+1` | блюмовы (`PrimeType::BBS`) |
| неглаткость `ord(hs)` | **по построению** | статистически |
| `|p − q|` | `≥ |p| − 100` (FIPS 186-4 B.3.1) | `≥ |n|/2 − 2` — **строже нашего** |
| проверка чужого `n` | нечётность и длина | **нет никакой** |
| проверка своего ключа | простота, длины, расхождение простых | нет |
| откуда берётся `hs` | **выводится из `n` на месте** | приезжает в публичном ключе |
| вырожденный `hs` | `DegenerateHs`, точный предикат | **не проверяется** |
| показатель при расшифровке | `mpz_powm_sec` | не проверял |
| канал по весу показателя | закрыт | не проверял |
| кэш-канал | закрыт | не проверял |
| канал по ведущим нулям | **открыт, ~0.36 бита** | не проверял |

### Что за этим стоит

**Главное различие — `hs` приезжает или выводится.** У `heu` публичный
ключ упакован как пара `(n_, h_s_)` и распаковывается без единой
проверки (`public_key.h:86-87`, следом сразу `Init()`). То есть
шифрующая сторона ОБЯЗАНА доверять чужому `h_s_`. Проверить его нельзя:
проба на гладкость с границей `B` удостоверяет лишь `√B` работы, а стоит
`π(B)·|n|` возведений.

Наш `from_n` берёт с провода только `n` и выводит `hs` сам. Отравленный
модуль по-прежнему даёт отравленный `hs` — от этого вывод на месте не
спасает, — но целый класс возможностей исчезает без единой проверки.

**Вырожденный `hs`.** `heu` требует лишь `gcd(x, n) = 1`
(`key_generator.cc:44-47`). При `x = 1` выходит `h = −1`, `h_s = n²−1`, и
рандомизация схлопывается до одного бита: `hs^r ∈ {1, n²−1}`. Вероятность
ничтожна, но проверки нет; у нас это ловит `DegenerateHs`, и предикат
точный, а не эвристика — при безопасных простых `ord(hs) ≤ 2` есть
единственное достижимое вырождение.

**В одном месте `heu` строже нас.** Расхождение простых: у них
`≥ |n|/2 − 2` бит (при 2048 это 1022), у нас `≥ |p| − 100` (924).
Обе величины закрывают Ферма с колоссальным запасом, но требование у них
жёстче, и это надо называть, а не замалчивать.

**Чего я НЕ утверждаю.** Про постоянство времени у `heu` — ничего. В его
собственном коде запроса постоянного времени нет нигде, но возведение
уходит в SPI длинной арифметики (`bigint_spi`, по умолчанию openssl), а
его исходников я не читал. Отсутствие запроса — не доказательство
отсутствия свойства.

Разбор по коду: `heu/library/algorithms/paillier_zahlen` (Apache 2.0,
это и есть `SchemaType.ZPaillier`) против `fast-paillier 0.3.2`
(MIT OR Apache-2.0), на котором стоит наш пакет.

Замерено на одном наборе, ключ 2048 бит, Python 3.10, один поток:
шифрование **0.69 мс** у `heu` против **9.36 мс** у нас. Разница
тринадцатикратная при том, что обе считают длинной арифметикой на C.
Значит дело не в языке — ниже разобрано, в чём.

## Шифрование

Обе стороны считают `c = g^m · r^n mod n²`, но по-разному.

### `g^m` — паритет

При `g = n+1` бином даёт `g^m ≡ 1 + m·n (mod n²)`: одно умножение
вместо возведения в степень. Делают обе.

`heu` (`encryptor.cc:44`):

```cpp
BigInt gm = pk_.n_ * m + 1;  // no need mod
```

`fast-paillier` (`encryption_key.rs:75`):

```rust
let a = (Integer::one() + &x * self.n()) % self.nn();
```

### `r^n` — здесь и лежит разрыв

`fast-paillier` (`encryption_key.rs:78`) считает буквально:

```rust
let b = nonce.pow_mod_ref(self.n(), self.nn())
```

Основание `nonce` **случайное**, показатель `n` — 2048 бит, модуль `n²`
— 4096 бит. Полное возведение в степень, и ничего предвычислить нельзя:
основание каждый раз новое.

`heu` (`encryptor.cc:26-31`) считает иначе:

```cpp
BigInt Encryptor::GetRn() const {
  BigInt r = BigInt::RandomExactBits(pk_.key_size_ / 2);
  return pk_.m_space_->PowMod(*pk_.hs_table_, r);
}
```

Три отличия сразу, и каждое режет цену:

1. **Основание фиксированное.** Вместо `r^n` берётся `h^r`, где `h`
   заготовлено при генерации ключа. Это вариант Дамгорда–Жюрика, а не
   самодеятельность. Но «неразличимость сохраняется» — не следствие
   одной DCRA: нужно ДОПОЛНИТЕЛЬНОЕ предположение о коротком
   показателе, и оно выписано первым пунктом в
   `docs/short-exponent-security.md`. Безусловно эту фразу читать
   нельзя.
2. **Таблица окон.** `hs_table_` — предвычисленные степени фиксированного
   основания. Возможна ровно потому, что основание не меняется.
3. **Показатель вдвое короче.** `key_size_ / 2` — 1024 бита вместо 2048.

Итого вместо возведения случайного основания в 2048-битную степень —
табличное возведение фиксированного основания в 1024-битную. Отсюда и
берётся тринадцатикратная разница.

### Пространство Монтгомери

`heu` держит модуль в `m_space_` и считает `MulMod`/`PowMod` в нём
(`encryptor.cc:46,49`), с явными переходами `MapIntoMSpace` /
`MapBackToZSpace`. `fast-paillier` пользуется обычными `%` и `.modulo()`
поверх GMP.

**У нас этот приём был реализован и откачен по замеру.** Записано здесь,
чтобы следующий читатель не пробовал заново.

| n = 10 000, модуль 2048 | эл/с шифрования |
|---|---|
| до обоих приёмов | 1 190 |
| + таблица окон | **4 576** |
| + таблица и Монтгомери | 3 872 |

Монтгомери **замедлил на 15 %**. Причина в уровне, на котором он
написан: REDC поверх `rug::Integer` собирается из тех же полноразмерных
операций — два умножения, сложение и сдвиг вместо одного умножения и
одного деления. `mpz_tdiv_r` в GMP стоит дешевле, чем два лишних
умножения по 4096 бит.

У `heu` тот же приём выигрывает потому, что лежит **на лимбах**, внутри
`m_space_`, а не поверх обёртки над `mpz`. Повторить это у нас значило
бы спуститься к `gmp-mpfr-sys` и работать с `mp_limb_t` напрямую — то
есть писать своё умножение по модулю со всеми обязательствами по
постоянству времени. Это уже не «чистая арифметика», как обещала
таблица ниже.

Арифметика при этом была верна: шесть тестов на равенство с `pow_mod`,
включая исчерпывающий перебор всех 65536 показателей двух байт,
проходили. Снято не из-за ошибки, а из-за того, что на этом уровне
приём не окупается.

## Расшифровка

Здесь **обе** делают китайскую теорему об остатках: `heu`
(`decryptor.cc:38-47`) — явно, порознь по `p²` и `q²`, со сборкой через
`p_inv_mod_q_`; `fast-paillier` (`decryption_key.rs:80`) — тем же
приёмом, но спрятанным в `crt_mod_nn.exp`.

Числа менялись дважды, и обе цифры стоит держать рядом:

| | мс, ключ 2048 |
|---|---|
| `heu` | 2.79 |
| мы на `fast-paillier` | 5.32 |
| мы на своей расшифровке | **3.65** |

Своя реализация делает то же самое, но возводит через `mpz_powm_sec`
вместо `mpz_powm` — это единственное отличие по существу. Показатель
здесь выведен из `λ`, то есть из ДОЛГОВРЕМЕННОГО секрета ключа, а
документация GMP для секретных показателей требует именно `_sec`:
`mpz_powm` обращается к таблице по битам показателя.

Цена этого замерена отдельно, на тех же длинах, что в компонентах
китайской теоремы (`benches/secure_pow.rs`, медиана трёх серий по сто):

| длина `n` | `powm`, мкс | `powm_sec`, мкс | отношение |
|---|---|---|---|
| 2048 | 1195–1245 | 1840–1934 | **1.54–1.55** |
| 3072 | 3573–3793 | 5965–6109 | **1.61–1.67** |

Абсолютные величины даны вилкой по двум прогонам, отношение — жирным:
устойчиво именно оно, а машина между запусками гуляет на 4–6 %.

Два возведения при 2048 битах дают 3.7–3.9 мс при расшифровке 3.65: то
есть в расшифровке практически ничего, кроме них, и нет. Разводить эти
две величины точнее прогоны не позволяют — знак расхождения между
запусками меняется (то целое дешевле суммы частей на 1 %, то на 5 %),
и это ровно та разница, которую даёт переход между процессами.

С обычным `powm` вышло бы около 2.4 мс, и мы были бы БЫСТРЕЕ `heu`.
Отставание 3.65 против 2.79 — плата за свойство, а не проигрыш в
алгоритме.

Утверждать, что у `heu` этого свойства нет, я не буду: в его собственном
коде запроса постоянного времени нет нигде, но возведение уходит в SPI
длинной арифметики (`bigint_spi`, по умолчанию openssl), а его исходников
я не смотрел. Проверяемое утверждение здесь только одно — про нас.

## Что переносим

| приём | у нас | у `heu` | итог |
|---|---|---|---|
| `g^m = 1 + m·n` | было | есть | переносить нечего |
| КТО при расшифровке | было | есть | переносить нечего |
| фиксированное основание `h` вместо `r^n` | **перенесено** | есть | требовало правки генерации ключа |
| короткий показатель `n/2` бит | **перенесено** | есть | следствие перехода на `h` |
| таблица окон для `h` | **перенесено** | есть | чистая арифметика, дала 3.8× |
| пространство Монтгомери | **отвергнуто по замеру** | есть | поверх `mpz` замедляет на 15 % |

Первые два были у нас изначально. Три следующих перенесены, шестой
проверен и отвергнут — разбор выше.

### Что дал перенос, и в чём я сначала соврал числами

Считать надо **по ядру**, а не сравнивать наш параллельный
`encrypt_many` с питоновским циклом у `heu`. Замер на одном ключе 2048,
одних данных, одном окружении:

| | эл/с |
|---|---|
| наши, 12 потоков | 4403 |
| наши, один поток | **686** |
| `heu`, последовательный цикл | **1378** |

Числа перемеряны после перехода на постоянное по времени чтение таблицы
(`src/fast.rs`): было 4454 и 683, стало 4403 и 686 — то есть закрытие
кэш-канала не стоило ничего измеримого. Отдельным замером на самом
возведении цена вышла 1–3 % (`benches/window_select.rs`); в сквозном
прогоне она тонет в разбросе.

**По ядру `heu` быстрее нас вдвое.** Отрыв «втрое» был сопоставлением
разного, и это моя ошибка. Верное утверждение: приёмы сократили
отставание с тринадцатикратного до двукратного.

Масштабирование по потокам — 693 / 1331 / 2567 / 4076 / 4393 при 1, 2,
4, 8, 12: ×6.3 на двенадцати ядрах, эффективность падает с 96 % до
53 %. Уплощение после восьми — SMT плюс давление на память: таблица при
2048 битах около 2 МБ, и все потоки читают её одновременно. То есть
таблица выигрывает в одном потоке и хуже масштабируется.

Про точность я соврал так же, и дважды — сперва масштабом, потом
эталоном.

Масштабом: ошибка суммы у `heu` больше нашей не из-за алгоритма, а
из-за умолчания кодировщика — у них `scale = 1e6`
(`plain_encoder.h:48`), у нас `SCALE = 1e8`.

Эталоном: я сравнивал результат с точной суммой ОКРУГЛЁННЫХ значений.
Но это ровно то, что схема обязана дать по построению, — измерялась
гомоморфность, которая точна, а не ошибка кодирования. Отсюда и взялась
цифра `1.0e-08` на миллионе слагаемых: подпись входов без ошибки
округления, а не свойство схемы. Верный эталон — точная сумма ИСХОДНЫХ
чисел в `Fraction`.

С верным эталоном и на одних и тех же входах (1000 чисел, `σ = 100`,
`|n| = 2048`, `benches/measure.py`):

| | круг | сумма 1000 |
|---|---|---|
| `heu`, `scale = 1e6` | 2.12e-07 | 3.56e-05 |
| `heu`, `scale = 1e8` | 1.82e-09 | 4.53e-07 |
| наша, `SCALE = 1e8` | **1.82e-09** | 3.07e-07 |

Круг совпадает до последней цифры. И здесь я написал третью неправду:
«разницу в сумме записывать в преимущество нельзя, это один розыгрыш
случайного блуждания на каждую строку; оба кодировщика округляют к
ближайшему».

Розыгрыш там не один и не случайный: **обе строки берут один и тот же
файл входов**, что и доказывает совпадение колонки «круг» до последней
цифры. А правила округления РАЗНЫЕ, и это проверено различающим
наблюдением, а не выведено из чисел (`benches/acc_rounding.py`).

Проба — значение, у которого масштабированная величина имеет дробную
часть 0.7: усечение её отбросит, округление добавит единицу.

| | `1.0000007` | `−1.0000007` | вывод |
|---|---|---|---|
| `heu` | `1.0000000` | `−1.0000000` | усечение к нулю |
| наша | `1.0000010` | `−1.0000010` | к ближайшему |

Это следует и из кода: `PlainEncoder::Encode` (`plain_encoder.h:60`)
считает `cleartext * scale_` в `double` и кладёт результат в целочисленный
`Plaintext`, а преобразование `double → целое` в C++ усекает к нулю.

### Чем это оборачивается на знакопостоянных данных

Усечение смещает КАЖДОЕ слагаемое вниз по модулю — на `1/(2·scale)` в
среднем. На симметричном входе сносы разных знаков гасятся, и обе
библиотеки растут как `√k`; поэтому на первой таблице разница выглядит
розыгрышем. Но входы федеративного обучения сплошь и рядом
знакопостоянны: счётчики бакетов, квадраты градиентов, суммы модулей.
Там сносы складываются, и ошибка растёт ЛИНЕЙНО.

Замерено (`benches/measure.py`, вход `uniform(0, 1000)`, масштаб
`1e8` у обеих, эталон — точная сумма исходных чисел):

| k | `heu` | наша | снос `k/(2·scale)` | блуждание `√(k/12)/scale` |
|---|---|---|---|---|
| 1 000 | 4.98e-06 | 1.95e-08 | 5.00e-06 | 9.13e-08 |
| 10 000 | 5.02e-05 | 1.42e-07 | 5.00e-05 | 2.89e-07 |
| 100 000 | 5.00e-04 | 1.17e-06 | 5.00e-04 | 9.13e-07 |

Ошибка `heu` совпадает со сносом до третьей цифры на всех трёх
размерах; наша держится на уровне блуждания. **На ста тысячах
неотрицательных слагаемых мы точнее в 430 раз**, и это не розыгрыш, а
разные правила округления.

Настоящий результат был похоронен моим же выводом. Форма «оба
несмещённы» звучит осторожно и потому выглядит честной — но осторожная
неправда остаётся неправдой.

Как ошибка растёт — замерено отдельно (`benches/measure.py`,
`SCALE = 1e8`, эталон точный):

| k | ошибка | `√(k/12)/SCALE` | отношение |
|---|---|---|---|
| 1 000 | 3.09e-08 | 9.13e-08 | 0.34 |
| 10 000 | 4.73e-08 | 2.89e-07 | 0.16 |
| 100 000 | 9.62e-07 | 9.13e-07 | 1.05 |
| 1 048 576 | **2.60e-06** | 2.96e-06 | 0.88 |

Отношение болтается около единицы и НЕ растёт — это и есть довод, а не
совпадение отдельных чисел: каждая клетка тут единичный розыгрыш, и
разброс в ней большой. Смещение даже в один младший разряд на слагаемое
дало бы на `2^20` величину порядка `1e-02`, то есть отношение около
`3·10^3`. Наблюдается `0.88`.

Практический предел отсюда: при `SCALE = 1e8` миллион слагаемых стоит
около `3e-06` абсолютной ошибки. Это шум кодирования, и он не зависит
от длины ключа — только от масштаба.

**И только пока `|v| ≲ 2^53/SCALE`, то есть примерно до `9e7`.** Выше
этой величины `value * SCALE` не представимо в f64 точно, округляется
само, и ошибка перестаёт быть абсолютной — становится относительной:
около `6e-7` при `|v| ~ 1e10` и около `1e-2` при `1e14`.

Оговорки здесь не было вовсе, а замер (`benches/measure.py`) идёт
на входе `±1000` — то есть ровно там, где модель и держится. Проверить
модель там, где она верна, и записать её без условия — это ровно тот
приём, за который в этом же документе разобрана история с эталоном
суммы.

Где сравнение сопоставимо и мы действительно быстрее — сложение: 1000
слагаемых за 0.0071 с против 0.0106 с, и наш цикл **однопоточный**.

Главный перенос — переход с `r^n` на `h^r` с таблицей и коротким
показателем. Он трогает **схему**, а не только арифметику: `h`
порождается при генерации ключа, и его корректность — условие
стойкости. Приём стандартный и опубликованный, но вводить его надо с
проверкой, а не «по аналогии».

Здесь стояло: «Пространство Монтгомери и таблица окон безопасны: они не
меняют результат, только скорость». Это неверно, и неверно ровно тем
способом, против которого написан весь `short-exponent-security.md`:
**«не меняет результат» и «не меняет наблюдаемое» — разные вещи.**

Таблица окон в первой редакции пропускала нулевые цифры, и число
умножений равнялось числу ненулевых полубайт СЕКРЕТНОГО показателя.
Замерено при `|n| = 2048`: от 0.2 мкс на пустом показателе до 1576 мкс
на полном, линейно, по 6.1 мкс на цифру — 0.4 % полного времени, много
выше шума.

Заявленный запас это не пробивало: точное знание веса `r` даёт около
четырёх бит из 1024, сильная форма утечки — около 86, и остаётся много
выше границы `2^512`. Но «не пробивает» и «безопасно» — разные
утверждения.

Пропуск снят: умножение делается на каждом окне. Но первая попытка это
**не сработала**, и ошибка стоит записи. Я положил в таблицу единицу —
и замер дал подорожание 0.6 % вместо ожидавшихся 6.7 %. Я прочёл это
как хорошую новость. На деле недостающие шесть процентов были той
работой, которая не делается: `result * 1` GMP считает за `O(лимбов)`,
а следующий `% n²` возвращается сразу. Наклон времени по весу
показателя остался прежним — 6.32 мкс на цифру против 6.1 до «правки».

**Дешевле ожидаемого — это не подарок, а сигнал.**

Работает полноразмерный вычет: в нулевой записи лежит `n² + 1`. Замер
после — наклон **−0.186** мкс на цифру, разброс 2.3 % без тренда, то
есть шум. Цена свойства — 2.1 % (679 → 665 эл/с в потоке). Прогон
оставлен в репозитории: `tests/timing_channel.rs`, признак —
наклон, а не абсолютное время.

Постоянного времени это НЕ даёт и не заявляется. Каналов было названо
три: по весу показателя (закрыт), кэш-канал (закрыт позже, разбор ниже)
и по позиции ведущих нулей — он остаётся открытым.

**Ведущие нули.** Цикл стартует с единицы, и пока младшие цифры
нулевые, накопитель однолимбовый. Замерено: −6.33 мкс на ведущий нуль
при ФИКСИРОВАННОМ весе. Канал по весу закрыт, канал по позиции — нет.
Проверено и то, что очевидное лечение не работает: старт с `n² + 1`
даёт −6.56, потому что приведение возвращает каноническую единицу.

Единственное известное лечение — избыточное представление, где единица
не однолимбовая, то есть **форма Монтгомери, отвергнутая выше по
скорости**. Связь прямая, и прятать её нельзя.

Остаток: энтропия длины ряда ведущих нулей около **0.36 бита** из 1024,
против запаса `2^512` — ничто. Допущен осознанно, сторожится
`tests/timing_channel.rs` на нерост.

**Кэш-канал — закрыт, и цена его была посчитана неверно.** Запись
выбиралась по индексу, равному цифре, значит адрес обращения к памяти
зависел от секрета. Здесь стояло: «закрыть значило бы читать всю строку
на каждом окне — платить в шестнадцать раз».

Это смешивает «прочитать шестнадцать записей» с «сделать шестнадцать
умножений». Умножение остаётся ОДНО; добавляется потоковое чтение восьми
килобайт, которое против умножения на 4096 битах почти ничего не стоит.

Строка теперь лежит 64-битными словами и читается целиком, нужная запись
выбирается арифметической маской без единого ветвления
(`src/fast.rs::select_entry`). Замерено на одних `hs`, `n²` и показателе,
результаты сверены на равенство (`benches/window_select.rs`):

| `|n|` | по индексу | маской | отношение |
|---|---|---|---|
| 2048 | 1432 мкс | 1445 мкс | **1.01** |
| 3072 | 4281 мкс | 4425 мкс | **1.03** |

Не шестнадцать раз, а один-три процента; в сквозном прогоне не видно
вовсе. Число, на которое опиралось решение оставить канал открытым, было
завышено более чем на порядок.

Укладка словами, а не байтами — не мелочь: с побайтным чтением то же
самое стоило **+26 %**. Цена здесь упирается в число итераций, а не в
объём данных.

Чего в этом списке **нет** намеренно: заготовленного запаса готовых
`r^n`. Он дал бы ещё, но повторное использование `r` ломает
семантическую безопасность, и вводить его можно только с явной
гарантией однократного расхода каждого значения.
