# paillier

Аддитивно-гомоморфное шифрование Paillier для Guardora: своя реализация
на Rust поверх GMP (через [`rug`][rug]), привязка к Python через pyo3.

**Криптография здесь, а не в зависимости.** Порождение безопасных
простых, шифрование, гомоморфное сложение, расшифровка по китайской
теореме об остатках — всё в `src/`. Крейт `fast-paillier` остался
только в `dev-dependencies`, эталоном для тестов: реализация, сверяемая
сама с собой, ничего не доказывает.

## Это НЕ учебниковый Paillier

Читать до использования. Схема — вариант **Дамгорда–Жюрика с коротким
показателем**, тот же, что у `heu`:

```
c = (1 + m·n) · hs^r  mod n²,   hs = h^n,  h = −x² mod n,  |r| = |n|/2
```

вместо учебникового `c = g^m · r^n mod n²`.

Отсюда следствие, которое надо знать: **неразличимость шифротекстов
опирается не на одну DCRA**. Нужно ДОПОЛНИТЕЛЬНОЕ предположение — о том,
что короткий показатель в подгруппе, порождённой `hs`, неотличим от
полного. Предположение стандартное и опубликованное, но оно есть, и
безусловной фразы «стойко по DCRA» здесь сказать нельзя.

Полный разбор, включая то, что от ключа требуется и чего эта схема НЕ
даёт: [`docs/short-exponent-security.md`](docs/short-exponent-security.md).

### Постоянного времени НЕТ

Закрыты два канала: по весу секретного показателя и кэш-канал (строка
таблицы читается целиком, запись выбирается арифметической маской).
Открыт один — по числу ведущих нулей показателя, около **0.36 бита** из
1024. Он назван, замерен и сторожится тестом на нерост; единственное
известное лечение — форма Монтгомери, отвергнутая по скорости.

Расшифровка возводит через `mpz_powm_sec`: показатель там выведен из
`λ`, то есть из долговременного секрета ключа.

## Что это даёт по числам

Ключ 2048 бит, один набор, одна машина, N = 200:

| | шифрование | без параллелизма | сложение | расшифровка | шифротекст |
|---|---|---|---|---|---|
| **этот пакет** | **0.23 мс** | 1.46 мс | **6.7 мкс** | 3.65 мс | 512 Б |
| `heu` (C++) | 0.71 мс | 0.71 мс | 9.8 мкс | 2.79 мс | 524 Б |
| `phe` (Python + gmpy2) | 9.83 мс | 9.83 мс | 56.0 мкс | 2.71 мс | 1233 Б |
| `lightphe` (чистый Python) | 131.7 мс | 131.7 мс | 54.5 мкс | 105.6 мс | 1232 Б |

Колонка «шифрование» у нас — двенадцать потоков, у остальных
параллелизма нет вовсе. **По ядру `heu` быстрее нас вдвое** (1378
против 686 эл/с); честное утверждение — что перенос его приёмов сократил
отставание с тринадцатикратного до двукратного. Разбор:
[`docs/heu-comparison.md`](docs/heu-comparison.md).

Расшифровка у нас медленнее `heu` не по алгоритму: с обычным `mpz_powm`
вышло бы около 2.4 мс. Разница — плата за безопасное к показателю
возведение.

## Точность

Кодирование — неподвижная точка с масштабом `1e8`, округление **к
ближайшему**.

Правило округления выбрано не по вкусу. `heu` усекает к нулю
(проверено различающим наблюдением, `benches/acc_rounding.py`), и на
ЗНАКОПОСТОЯННЫХ данных — счётчиках бакетов, квадратах градиентов — это
даёт снос в одну сторону, то есть ошибку, растущую ЛИНЕЙНО по числу
слагаемых:

| слагаемых | `heu` | этот пакет |
|---|---|---|
| 1 000 | 4.98e-06 | 1.95e-08 |
| 10 000 | 5.02e-05 | 1.42e-07 |
| 100 000 | 5.00e-04 | 1.17e-06 |

Оба при масштабе `1e8`. На симметричном входе разницы нет: сносы разных
знаков гасятся, и обе растут как `√k`.

Границы, за которыми модель ломается:

* **снизу** — всё, что по модулю меньше `1/(2·SCALE)`, кодируется нулём;
* **сверху** — ошибка остаётся абсолютной, пока `|v| ≲ 2^53/SCALE ≈ 9e7`;
  выше `value * SCALE` округляется само, и ошибка становится
  относительной;
* **сумма** — принимается не более `2^20` слагаемых, и наибольший
  открытый текст ужат под этот запас (`plaintext_bound_bits`).

## Почему не готовая библиотека

**`heu`** быстрее нас по ядру, но под CPython 3.13 не работает:
`sf-heu==0.6.0b0` помечена `cp310` и не ставится; `sf-heu==0.4.2b0`
помечена `cp38-abi3`, ставится и падает при импорте на
`_PyObject_NextNotImplemented` — символе, удалённом из CPython 3.12. То
есть метка `abi3` там ложная.

**`phe`** вчетверо медленнее в одном потоке и вдвое длиннее шифротекст.
Точность у него на порядки выше — экспонентное кодирование против
фиксированного масштаба; это стоит помнить, если понадобится широкий
динамический диапазон.

**`fast-paillier`** — крейт, с которого пакет начинался. Ушёл в
`dev-dependencies`, потому что через его `Plaintext` числа ходили
туда-обратно через ДЕСЯТИЧНУЮ СТРОКУ (`to_string().parse()`), а
короткого показателя и таблицы окон в нём нет вовсе.

## Проверки

```
cargo test --release
python -m pytest
```

Прогоны (не тесты, запускаются руками) — в `benches/`: сравнение
библиотек, цена постоянного по времени чтения, цена `mpz_powm_sec`,
влияние длины показателя, накопление ошибки.

## Сборка

```
cargo build --release
```

Готовый `target/release/libpaillier.so` кладётся в `site-packages` под
именем `paillier.so`.
